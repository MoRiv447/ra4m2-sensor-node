## 验收日志（2026-10-10 20:22 串口原样）

```
[WiFi] << OK
[WiFi] << +NWMQCL:1
--- sample #1   t = 10.0s ---（传感器数据照常，略）
[WiFi] << +NWMQMSG:RA4M2;lux=5.8;ldr=2.8;T=24.9;RH=50.9,notmes/ra4m2,36
```

判读：
- `OK` —— 开机探测应答（链路双向通）；
- `+NWMQCL:1` —— **MQTT 已连接 broker**；同时说明**模块的配网 + broker 配置掉电后依然保存**
  （挂了两天的疑问，"重上电配置是否保存"——答案：保存）；
- `+NWMQMSG:<payload>,<topic>,<len>` —— 订阅回环事件：模块把"自己发布 → 经 broker → 自己订阅收回"
  的帧报了出来。payload **36 字节**，与同屏 sample 帧逐项吻合（BH1750 5.8 / LDR 2.8 / DHT 24.9 / 50.9）
  ⇒ **帧确实过了 broker**（不只是"发出去"）。

上报格式（每 10s 一帧）：
`RA4M2;lux=<BH1750>;ldr=<光敏电阻>;T=<DHT>;RH=<DHT>`（分号分隔——模块 payload 禁逗号）

## 联调排障链（本日，按时间）

1. **现象 A：MCU 与模块零通信**（`[WiFi] <<` 全无；两个线序方向都试过、一样静默）。
   - 排查：先用工具单测证"模块活着"（`AT`+CRLF → `OK`；`AT?` → `ERROR:-1` 是不认的蓝牙语法）；
     再用户蜂鸣实测 →
     **根因：标 1 手焊排针的两个数据脚虚焊开路（VCC/GND 通、数据脚不响）——信号从未出 MCU。**
   - 修复：信号线改落 **标 2 第 4/5 孔** → `[WiFi] << OK` 打通。
2. **现象 B：`ERROR:-6`（数据上报被模块拒绝）**。
   - 根因（代码）：`wifi_bridge_init` 把 `AT` 与 `AT+NWMQCL=1` 背靠背连发，UART 异步发送 +
     忙保护把第二条**静默丢掉**（证据：两条命令只回一条 `OK`）→ MQTT 从未连接 → 上报全被拒。
   - 修复（`wifi_bridge.c/.h`）：① 第二条前 `wifi_wait_tx_idle()`；
     ② 未连上时每 10s 自动重试 `AT+NWMQCL=1`，直到 `+NWMQCL:1`；③ 连上后才发数据帧。
3. 修复后一次通过（见上方验收日志）。

## 教训（可写进帖子）

- **手焊排针必须逐脚蜂鸣验证**——"看起来焊上了"和"电气上通了"是两回事；本次 VCC/GND 正常、
  唯独两个数据脚开路，极具迷惑性（供电正常、模块活着、就是不通）。
- **异步串口发送不能背靠背连发**：忙保护会丢掉"前一条还没发完时进来的下一条"；
  周期任务要留重试（自愈），别假设一次性发成功。
- 两处位置"同网络双出口"时，优先选**出厂焊点 + 有历史使用记录**的那一处。
